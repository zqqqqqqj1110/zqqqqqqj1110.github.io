# Workflow & Agent Harness｜精简版面试八股（15 题）

> 面向：AI Agent / 大模型算法岗。主线：**Workflow 设计与可靠性**；Harness 只掌握必要概念。  
> 标记：**P0** 必会（1—11），**P1** 常见追问（12—15）。  
> 项目题以“文档识别 → 分块 → 知识图谱 → 校验/复查”的四阶段文档处理系统为例；具体技术栈与线上指标以本人实际实现为准。

## 二、标准答案（面试口述版 + 必要追问）

### 1. Workflow 是什么？和单次 LLM 调用有什么区别？
**口述：** Workflow 是把任务拆成多个有依赖关系的步骤，并按预设控制流编排模型调用、工具调用、判断及数据传递的机制。单次 LLM 调用通常只有一次输入输出；Workflow 能管理多个节点、分支、失败恢复和中间结果，更适合复杂但步骤明确的任务。

**追问：** Workflow 不等于所有节点都用 LLM；其中可以有确定性代码、API、检索、人工审核。

### 2. Workflow 与自主 Agent 的区别？
**口述：** Workflow 的总体步骤和分支主要由系统预先设计，Agent 则可由模型根据中间结果自主决定下一步调用什么工具、是否继续或如何调整计划。Workflow 更可预测、易调试；Agent 对开放式任务更灵活，但不确定性、时延和成本一般更高。

**追问：** Workflow 的某个节点仍可使用 Agent 或模型驱动路由，不是“完全没有自主性”。

### 3. 常见 Workflow 编排模式？
**口述：** 常见的有顺序流水线（Sequential）、条件路由（Routing）、并行（Parallel）、主控协调子任务（Orchestrator–Workers）和生成—评估—修正循环（Evaluator–Optimizer）。选择由任务依赖决定：强依赖用顺序，可独立任务用并行，路径不确定时用路由或协调模式。

### 4. 如何设计节点输入输出？
**口述：** 先把任务拆成职责单一的节点，定义每个节点的输入输出 Schema、必要字段、失败状态与上游依赖；整体用 DAG 或状态机组织。节点交接前做格式校验和关键语义校验，避免靠自然语言约定接口。

**追问：** 需要明确版本号、文档 ID、页码/来源位置、节点状态等可追踪字段。

### 5. State、Memory、Checkpoint 的区别？
**口述：** State 是本次执行中的当前状态和中间数据；Memory 是跨轮次或跨任务保留、供模型或系统复用的信息；Checkpoint 是在关键步骤持久化的状态快照，用于失败后恢复。三者可以重叠，但概念不同。

### 6. 节点失败如何处理？
**口述：** 先区分瞬时错误与永久性错误。对超时或限流设置有限次数重试与指数退避；对格式错误先校验再修复；对无法恢复的错误走降级或人工介入。借助 checkpoint 从失败节点恢复，并通过幂等键避免重试产生重复写入。

**追问：** 幂等指相同操作重复执行，不会造成额外的不可预期副作用；写入图谱等外部操作尤其要考虑。

### 7. 如何阻断错误传播？
**口述：** 在节点边界做 Schema 校验、内容完整性校验和业务规则检查。对不合格输出不直接传下游，而是重试、回退到上游或进入人工复核；最终还需要端到端一致性验证。

### 8. 如何优化成本与时延？
**口述：** 先定位关键路径和高开销节点。无依赖步骤并行、重复结果缓存、批量调用、按任务难度选择模型，并设置 Token 与调用次数预算；但不能以牺牲必要质量校验为代价。吞吐由系统瓶颈决定，不是并行越多越好。

### 9. 如何评测 Workflow？
**口述：** 同时看节点级和端到端指标。节点级衡量识别准确率、切分完整率、图谱关系质量、校验检出率；端到端看最终任务成功率、正确率、错误传播率、P50/P95 时延、Token 成本、人工接管比例。要有固定测试集和失败案例归因。

### 10. Harness 是什么？核心组成？
**口述：** Agent Harness 是包围模型的运行与控制层，使模型能可靠地调用工具、维护上下文、处理多轮执行，并受到权限及安全约束。常见能力包括 Agent Loop、Tool Execution、上下文管理、State/Checkpoint、权限控制、日志与可观测性。Harness 不特指某一个框架，也不意味着模型必须完全自主。

### 11. Workflow、Agent、Harness 三者关系？
**口述：** Workflow 回答“整个任务按什么步骤执行”，Agent 回答“哪些决策由模型自主完成”，Harness 回答“这些模型和工具调用在什么运行机制下可靠执行”。它们是不同维度，可以组合：例如用 Workflow 固定文档处理主干，在某个节点内用 Agent 选择解析工具，由 Harness 负责调用、权限、状态和追踪。

### 12. ★ 项目：为什么采用 Workflow，而不是完全自主的 Agent？
**推荐口述（依照已描述的项目结构）：** 这个文档处理任务有比较稳定的依赖顺序：先识别文档格式并解析，再分块，随后抽取知识并构建图谱，最后进行复查。后面的节点依赖前面的结构化结果，因此我用 Workflow 固定主干，控制输入输出和校验点。这样做一是便于逐阶段定位错误，例如解析缺失、切分错位或图谱关系错误；二是可重复执行、便于评测；三是减少模型不必要的规划和工具选择开销。对于格式识别或异常处理这种存在局部不确定性的步骤，可以保留模型决策，但不把整个任务的调度完全交给自主 Agent。

**重要修正：** 不要说“Workflow 比 Harness 更好”；正确比较应为“Workflow 主干 vs 高自主度 Agent 执行”。Harness 是底层运行能力，可为两者提供支持。

### 13. ★ 项目：四阶段串联及出错处理？
**推荐口述：** 系统按“格式识别与解析 → 结构化切分 → 知识抽取/图谱构建 → 最终一致性复查”执行。第一阶段产出正文、元数据和定位信息；第二阶段保留块与原文位置的映射；第三阶段将块中的实体关系写入图谱，并保留来源证据；第四阶段对照原文、切分块和图谱/答案检查。如果发现原文解析缺失，回到解析节点；若是分块丢失或错位，回到切分节点；若来源正确但关系抽取或回答错误，重新抽取或复核。实际回答应只陈述你真正实现了的校验/重试逻辑，不要把建议设计说成已上线功能。

### 14. ★ 为什么 Workflow 而不是 Harness？
**推荐口述：** 我会先澄清两者不是替代关系。Workflow 是业务流程编排，Harness 是 Agent 的执行支撑层。我的项目重点在于多阶段文档处理的可控数据流，所以架构上选择 Workflow 固定步骤；运行时仍可能需要 Harness 式能力，如工具调用、日志、错误处理和状态管理。若面试官意在问为什么不做自主 Agent，我的理由是该任务步骤相对明确，稳定性、可追踪性与成本比自由规划更重要。

### 15. 什么时候增加 Agent 自主性或 Harness 能力？
**口述：** 当用户目标开放、工具路径难以预先枚举，或执行需要边观察边调整计划时，可以增加 Agent 自主决策。随着流程变长、工具增多或引入长期运行任务，再增强 Harness 层的权限管理、持久化、Checkpoint、上下文压缩、观测与恢复。原则是按需求逐步增加复杂度，而不是为了“智能体”标签堆架构。
